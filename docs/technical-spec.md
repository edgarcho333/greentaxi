# GreenTaxi — техническое задание, версия 0.11

Дата: 9 октября 2026 года.

Документ описывает первую версию сайта бронирования поездок Гори ↔ Тбилиси и административной панели. Разделы 1–5 содержат согласованные требования. Раздел 6 отдельно фиксирует разумные defaults для текущей реализации: они дополняют требования, а не обозначают дополнительные решения пользователя. Незаданные значения перечислены в разделе 9. Сценарии приёмки описывают ожидаемое поведение и сами по себе не подтверждают прохождение проверок.

## 1. Назначение и доступ

- Пассажир отправляет заявку на места на определённую дату и время.
- Сотрудник рассматривает входящую заявку, назначает её в слот и этим подтверждает заказ.
- Все сотрудники имеют одинаковые права в административной панели.
- Публичный сайт и административная панель работают на грузинском языке.
- На первом этапе пассажиру не нужна регистрация или проверка телефона по SMS.
- Проверка номера по SMS предусмотрена на будущий этап. Подтверждение номера и подтверждение заказа оператором — разные действия.
- Способ уведомления пассажира о подтверждении отложен пользователем и требует отдельного решения.
- Назначение водителей, раздел водителей, расчёт стоимости и онлайн-оплата исключены из первой версии. На пассажирской странице есть информационная подпись об оплате на месте; платёжные данные не собираются.
- Сайт размещается на Vercel, постоянная production-база — Neon PostgreSQL. Создание проектов и публикация проверяются отдельно от готовности исходников.

## 2. Направления и адреса

| Направление | Посадка | Высадка |
| --- | --- | --- |
| Гори → Тбилиси | Адрес пассажира в пределах Гори, ввод текстом | Одна фиксированная точка в Дидубе — დიდუბე |
| Тбилиси → Гори | Одна из 3–4 фиксированных точек в Тбилиси | Адрес пассажира в пределах Гори, ввод текстом |

- Другие города в предоставленном макете — демонстрационные данные.
- Карта для ввода адреса не требуется: адрес Гори вводится текстом.
- Сотрудник вручную добавляет и редактирует фиксированные точки в настройках административной панели.
- Пока реальные названия и адреса не внесены, начальная конфигурация содержит три явно помеченные демонстрационные точки посадки в Тбилиси с грузинскими названиями. Это тестовые данные, а не утверждение о действующих остановках.
- Фиксированная высадка в Дидубе также редактируется в настройках. Точный адрес сотрудник внесёт позднее; начальное название — «დიდუბე».

## 3. Расписание

- В обоих направлениях действует постоянное ежедневное расписание.
- Базовые времена: 06:00, 07:00, 08:00, 08:30, 09:00, 09:30, 10:00, 11:00, 12:00, 13:00, 14:00, 15:00, 16:00, 17:00, 18:00, 19:00, 20:00, 21:00.
- В базовом расписании 18 слотов на день на каждое направление.
- Сотрудник может изменять постоянное расписание и задавать изменения для отдельной даты.
- Расписание каждого направления управляется отдельно.
- Сотрудник может добавлять заказы в слот без ограничения по количеству заказов и сумме мест.
- Сотрудник выбирает от 1 до 8 мест кнопками; пассажир на главной странице — от 1 до 4 счётчиком «− / +». Лимит относится к одному заказу и не ограничивает вместимость слота.
- Ручной заказ, подтверждение заявки и перенос сотрудником доступны на сегодня или завтра по времени Грузии. Телефонное обращение оформляется прямо в строке: рядом с «Сегодня / Завтра» есть календарь для любой будущей даты. В обоих случаях принимаются только ещё не наступившие действующие часы; просмотр расписания, история и пассажирский календарь сохраняются.

## 4. Пассажирская часть

### 4.1. Форма бронирования

Главная страница повторяет предоставленный пассажирский макет: светлый фон, большой заголовок «Гори ↔ Тбилиси», форма в виде билета, справа зелёный блок о маршрутах и инструкция с тремя шагами. Заголовки используют Dachi The Lynx, остальной текст — FiraGO. На мобильном форма располагается перед пояснениями, навигация раскрывается кнопкой; элементы помещаются по ширине экрана.

Форма разделена на три шага: поездка, адрес и контакты. «Продолжить» проверяет текущий шаг; можно вернуться назад и изменить данные без их потери. Заявка отправляется только на последнем шаге. В нижней части билета показываются выбранные дата, время и количество пассажиров. Сетка времени содержит все действующие слоты выбранной даты и направления, включая 08:30 и 09:30; прокрутка позволяет сохранить компактный вид макета.

Пассажир указывает:

1. Направление.
2. Дату.
3. Время из расписания выбранного направления и даты.
4. Количество мест счётчиком «− / +»: от 1 до 4.
5. Адрес посадки в Гори либо фиксированную точку посадки в Тбилиси — в зависимости от направления.
6. Адрес высадки в Гори для поездки из Тбилиси. Для поездки из Гори отображается фиксированная высадка в Дидубе.
7. Имя и телефон.

### 4.2. Отправка заявки

- Заявка получает статус «Ждёт подтверждения».
- Заявка поступает в отдельную очередь входящих административной панели.
- Выбранные пассажиром дата и время сохраняются как запрошенные; фактический слот назначает сотрудник.
- После отправки показывается сообщение на грузинском о приёме заявки и необходимости дождаться подтверждения оператора.
- Наличие заявки в очереди не означает, что заказ подтверждён.
- Публичная форма и API не возвращают сохранённые имя или адреса по номеру телефона. Автоподстановка профиля до SMS-проверки доступна только сотрудникам.

## 5. Административная панель

### 5.1. Дизайн

- Основа — предоставленный макет GreenTaxi: боковая навигация, верхние фильтры, выбор даты, выбор времени, таблица заказов и зелёные акценты.
- Раздел и фильтр водителей удаляются.
- Добавляется заметная кнопка «Создать заказ».
- В верхней панели «Новый заказ» и «Печать» показаны крупными зелёными кнопками с названиями и иконками; поиск по имени и телефону имеет компактную ширину.
- Даты, время, телефоны и числа отображаются в удобном для грузинского интерфейса формате.
- Заголовки, названия пунктов бокового меню, выход и крупная подпись под изображением используют присланный Dachi The Lynx Regular; основной текст, формы, таблицы и цифры — FiraGO. Эти же шрифты используются на пассажирском сайте, в HTML-превью и печатных отчётах.

### 5.2. Входящие заявки

- Очередь показывает заявки, ожидающие назначения в слот.
- Сотрудник видит данные пассажира, телефон, направление, запрошенные дату и время, количество мест, посадку и высадку.
- Сотрудник выбирает фактический слот. Назначение сразу подтверждает заказ и переносит его из входящих в список заказов этого слота.
- Повторное нажатие на действие подтверждения не должно создавать второй заказ.

### 5.3. Заказы по слотам

- Список фильтруется по направлению, дате и времени.
- Поиск работает по имени и телефону.
- В интерфейсе используются статусы «Ждёт подтверждения» и «Подтверждён»; удаление является отдельным действием с сохранением истории.
- Таблица показывает время, имя, телефон, количество мест, места посадки и высадки, статус и действия.
- Направление показывается там, где список может содержать оба направления.
- Оператор может редактировать адрес и телефон заказа и менять количество мест кнопками от 1 до 8. Поля имени в операторских формах нет; сохранённые ранее имена не удаляются.

### 5.4. Ручное создание заказа

- Поля расположены в порядке: локация, телефон, направление, количество мест, день, час. Имя не требуется и не запрашивается.
- Локация содержит текстовый адрес в Гори; для поездки из Тбилиси дополнительно выбирается действующая точка посадки в Тбилиси. При смене направления подпись адреса отражает посадку или высадку.
- Количество мест выбирается из восьми постоянно видимых кнопок «1–8». День выбирается из двух кнопок «Сегодня / Завтра» с датами по времени Грузии; календаря в форме нет.
- Все действующие часы выбранного дня показаны кнопками без выпадающего списка или отдельной прокрутки сетки. Для сегодня скрыты прошедшие часы и уже наступившее время. Доступность обновляется при открытой форме, в том числе при смене суток; устаревший выбор нельзя сохранить.
- Создание заказа в слоте сразу подтверждает его.
- Для адресов применяются те же правила направлений, что и в пассажирской форме.

### 5.5. Удаление и восстановление

- Удалённый заказ убирается из активных списков и сохраняется в истории.
- Сохраняются данные пассажира, адреса, количество мест, запрошенное время, назначенный слот и прежний статус.
- Сотрудник может восстановить заказ.
- Восстановление подтверждённого заказа в прежний действующий слот сохраняет историю, включая прошлую дату. При явном выборе другого слота действуют ограничения сегодняшнего и завтрашнего дня и будущего времени. Отключённый прежний слот требует выбора нового; перенос автоматически не выполняется.

### 5.6. Телефонные обращения с Android

- Дополнительный источник — телефон Redmi на Android 15 с SIM-картой. Устройство передаёт новые входящие SIM-звонки, на которые ответили; старые звонки не импортируются.
- Пропущенные, отклонённые и исходящие звонки не создают обращения. Звонки мессенджеров не входят в этот источник.
- После ответа на обычный входящий SIM-звонок сразу создаётся отдельное телефонное обращение во входящих, пока разговор продолжается. Из звонка известны номер, время и устройство. Имя клиента не требуется.
- Колонка «წყარო» заменяется выбором города отправления: Гори или Тбилиси, оба доступны. «მისამართი» показывает последний адрес посадки для выбранного города: текстовый адрес дома в Гори или одну из действующих точек посадки в Тбилиси. Эти предпочтения сохраняются независимо: адрес высадки в Гори не перезаписывает адрес посадки в Гори. Для поездки из Тбилиси дополнительно указывается адрес высадки в Гори. Отдельной колонки «ბოლო გაჩერება თბილისში» нет.
- Сразу после адреса располагаются оформление поездки: кнопки «Сегодня / Завтра», компактный календарь для другой будущей даты, карусель действующих будущих часов, выбор 1–8 мест, подтверждение и отказ. Выбор дня, времени и мест относится к новой поездке; прошлые часы скрыты и дополнительно проверяются сервером.
- Время и статус звонка объединены в компактную колонку; устройство сохранено. Очередь разделена на страницы. Введённые оператором данные не сбрасываются при автоматическом обновлении состояния звонка или смене страницы.
- После завершения обновляются фаза и длительность той же карточки. Оператор может создать подтверждённый заказ во время разговора; завершение звонка не меняет его поля. Повторные события каждой фазы не создают вторую карточку. Неоднозначные ожидающие звонки и перерывы наблюдения обрабатываются по подтверждённой записи журнала после завершения.
- Сотрудник дополняет данные прямо в строке и подтверждает заказ без открытия отдельной формы. Подтверждённый заказ связывается с обращением и исчезает из входящих. Отказ переносит обращение в историю с возможностью восстановления; он не завершает телефонный разговор.
- Повторная доставка того же события с устройства не создаёт второе обращение; повторное преобразование обращения не создаёт второй заказ.
- Необработанное телефонное обращение можно удалить в историю и восстановить во входящие без преобразования в заказ.
- Сотрудник подключает устройство через настройки панели и может отключить его доступ. Токен подключения показывается при создании устройства; его значение не сохраняется в репозитории или документации.
- Работа с физическим Redmi Android 15 требует отдельной проверки на устройстве. Проверки API и браузера с синтетическими событиями не подтверждают получение реального SIM-звонка.

### 5.7. Повторные пассажиры и автоподстановка

- Профиль пассажира связывается с нормализованным номером телефона и хранит имя, последний адрес в Гори и последнюю точку посадки в Тбилиси.
- Грузинский номер хранится как `568694879`, отображается как `568 69 48 79` без `+995`. Ввод с `+995`, `995`, `00995` и пробелами находит тот же профиль; номера других стран сохраняют свой международный код. Переход формата сохраняет идентификаторы заказов, удаления, историю и защиту от повторной доставки старого APK.
- При ручном создании заказа сотрудником и в карточке телефонного обращения адрес Гори и действующая точка Тбилиси доступны для автоподстановки. Сотрудник проверяет и при необходимости изменяет их перед сохранением. Имя не запрашивается; пустое имя нового операторского заказа не стирает сохранённое имя профиля.
- Отключённая или удалённая точка Тбилиси не подставляется как действующая; нужно выбрать актуальную точку.
- Дата, время, направление и количество мест прошлой поездки не становятся параметрами новой поездки автоматически. Их выбирают заново.
- Профиль обновляется действиями сотрудника с заказом. Необработанная публичная заявка или новый звонок не перезаписывают имя и сохранённые адреса.
- Профили и поиск по номеру доступны только авторизованным сотрудникам. Пассажирская форма не запрашивает и не показывает эти сведения до отдельной реализации подтверждения телефона по SMS.

### 5.8. Печать заказов

- В разделе заказов сотрудник открывает «ბეჭდვა», выбирает дату и печатает весь день либо конкретное время, включая 08:30 и 09:30. Если время уже выбрано в панели, оно подставляется в окно печати.
- По умолчанию используется текущее направление; можно выбрать оба направления.
- Отчёт содержит все подтверждённые активные заказы выбранной даты и времени независимо от поиска и страницы таблицы. Ожидающие заявки и удалённые заказы исключены.
- Расширенное окно печати показывает список из семи колонок: номер, время, имя, телефон, направление, места и адрес посадки. Колонка «ჩამოსვლის მისამართი» исключена из предпросмотра и печати. Строки и отступы уплотнены, адрес посадки переносится без сокращения; подводится итог заказов и мест.
- Для фиксированной посадки используются сохранённое в заказе название и текущий адрес точки из настроек.
- Кнопка «ბეჭდვა / PDF» заново получает актуальные данные и открывает системную печать браузера. Формат — A4, альбомная ориентация; сохранение PDF доступно через диалог браузера. Пустой отчёт или ошибка загрузки блокируют печать.

### 5.9. Список пассажиров и страница истории

- В разделе «მგზავრები» колонка «მისამართი» заменяет имя. Показывается последний адрес посадки: адрес дома в Гори либо настроенная точка Тбилиси. Город определяется последним созданным подтверждённым заказом, а адрес — сохранёнными предпочтениями этого города. Удаление старого заказа не меняет выбранный город.
- Пассажиры объединяются по нормализованному номеру телефона. Список поддерживает поиск адреса или телефона, страницы по 15/30/50 записей, переход к истории и ссылку для звонка. Имена клиента в этом разделе не показываются; старые значения в базе сохраняются.
- Адрес и кнопка истории открывают защищённую страницу `/admin/passengers/<номер>`. Прямую ссылку можно обновить или открыть после входа сотрудника. Возврат в список сохраняет поиск и страницу; работают переходы браузера назад и вперёд.
- Карточка показывает телефон, сохранённые адреса по городам и заказы с датой, временем, направлением, адресами, местами и статусом. Фильтры разделяют прошлые подтверждённые поездки, предстоящие поездки, ожидание подтверждения и удалённые записи; доступны также все заказы. Прошлая поездка определяется назначенным временем по Asia/Tbilisi, а не временем создания заявки.
- Счётчики заказов и мест списка учитывают активные записи, включая ожидающие заявки. Пассажиры, у которых осталась только удалённая история, также доступны со счётчиками 0. Удалённые записи не выдаются за состоявшиеся поездки.
- Просмотр не меняет профиль или заказы. Исторические названия остановок берутся из сохранённого заказа. Сведения другого номера и запоздалый ответ предыдущей карточки не попадают на страницу нового пассажира.
- Страница доступна сотрудникам в админке. Публичная пассажирская форма, регистрация и отложенная SMS-проверка остаются в прежнем объёме.

### 5.10. Несколько адресов и исторические заказы

- У одного номера сохраняется несколько адресов Гори и несколько настроенных остановок Тбилиси. Адреса Гори доступны для посадки и высадки; последние значения по умолчанию для каждого направления остаются независимыми.
- В телефонной очереди, создании и редактировании заказа оператор выбирает сохранённый адрес либо вводит новый вручную. Очистка и ручной выбор сохраняются при обновлении данных. Смена телефона подставляет варианты только соответствующего пассажира.
- Новый адрес сохраняется при подтверждённом заказе, в одной транзакции с заказом. Ожидающая заявка не меняет адреса. Повторы, отличающиеся регистром или пробелами, объединяются; уже сохранённые варианты не удаляются. Данные прежних подтверждённых поездок заполняют список при обновлении системы.
- Карточка пассажира показывает все сохранённые адреса по городам. Неактивные остановки Тбилиси исключаются из выбора новых заказов; исторические записи сохраняют прежние названия.
- Проверенные прошлые заказы переносятся приватным служебным заданием, сразу подтверждёнными и связанными с пассажиром по нормализованному номеру. Импорт сохраняет дату, время и число мест; более свежие адреса по умолчанию не заменяются старыми.
- Перед переносом проверяются дубли и спорные строки. Импорт транзакционный и повторяемый по пакету и строкам; последующие изменения оператора не сбрасываются повторным импортом. Обычные правила выбора сегодняшнего/завтрашнего дня остаются прежними. Отдельный исторический час не добавляется в постоянное расписание.

## 6. Defaults текущей реализации

Следующие правила выбраны для однозначного поведения первой реализации. Они отделены от требований, явно согласованных пользователем, и могут быть изменены при последующем обсуждении.

### 6.1. Расписание и переносы

- Все даты и времена считать в часовом поясе Asia/Tbilisi.
- Для новой пассажирской заявки доступны только действующие будущие слоты в Asia/Tbilisi. Для текущего дня показывать ещё не наступившие времена; прошлые даты недоступны пассажиру.
- Новые служебные назначения требуют будущего времени. Ручные формы предлагают сегодня и завтра; преобразование телефонного обращения дополнительно допускает другую будущую дату через календарь. Восстановление прежнего действующего исторического слота остаётся отдельным совместимым действием.
- Изменение на отдельную дату имеет приоритет над базовым расписанием для этой даты и направления.
- Отключение слота не удаляет связанные заказы. В админке такой слот остаётся виден с предупреждением, а оператор переносит его заказы вручную.
- При переносе подтверждённого заказа подтверждение сохраняется.
- При восстановлении ожидающей заявки она возвращается во входящие. Подтверждённый заказ возвращается в прежний слот, если он действующий, в том числе на прошлую дату; иначе сотрудник выбирает альтернативный действующий слот. Восстановление не включает отключённый слот автоматически и не переносит старую поездку в будущее автоматически.
- Счётчики дат и времени показывают количество активных назначенных заказов. Входящие заявки учитываются отдельным счётчиком. Количество мест в заказах показывается отдельно от количества заказов.

### 6.2. Остальные разделы макета

- «Пассажиры»: защищённый поиск по адресу и телефону, сохранённые адреса и отдельная страница связанных заказов с фильтрами истории. Это не требует регистрации пассажиров на сайте.
- «Аналитика»: количество заявок, подтверждённых заказов и мест по периоду и направлению; денежные показатели не используются.
- «Настройки»: постоянное расписание, изменения на даты, ручное добавление и редактирование фиксированных точек посадки и высадки. Демонстрационные точки явно обозначаются как тестовые до заполнения реальных данных.
- «История»: удалённые заказы с поиском и восстановлением.

### 6.3. Доступ и сохранность данных

- Сотрудники входят в защищённую панель по логину и паролю; все получают одинаковые права.
- Первый сотрудник создаётся на `/admin`: логин, имя и пароль длиной не менее 10 символов. До создания первого сотрудника данные панели недоступны.
- Для первичной настройки в production серверу требуется переменная окружения `ADMIN_SETUP_TOKEN`, созданная локально из не менее 32 случайных байт. Это внутренний секрет процесса запуска, а не параметр пассажирского сайта. Значение не сохраняется в документации или репозитории. После создания первого сотрудника переменную нужно убрать из production-окружения и перезапустить процесс либо выполнить новое развёртывание Vercel.
- Фиксировать сотрудника и время создания, подтверждения, редактирования, переноса, удаления и восстановления заказа.
- Перед удалением заказа запрашивать подтверждение. Кнопка отказа в строке телефонного обращения сразу переносит его в историю с возможностью восстановления.
- Повторная отправка одной формы и одновременная работа сотрудников не должны создавать дубликаты или повторно подтверждать одну заявку.
- Данные пассажиров доступны сотрудникам через защищённые серверные запросы; публичная форма не открывает списки заказов.

## 7. Предлагаемая модель данных

- **Сотрудник:** идентификатор, имя, данные входа, активность. Одна роль с одинаковыми правами.
- **Точка:** идентификатор, название, адрес, назначение — посадка в Тбилиси или высадка в Дидубе, активность.
- **Базовое расписание:** направление, время, активность.
- **Изменение расписания на дату:** направление, дата, добавленные или отключённые времена.
- **Слот:** определяется сочетанием направления, даты и времени; активность вычисляется из постоянного расписания и изменений на дату. Заказ сохраняет назначенные дату и время независимо от последующего отключения слота.
- **Заказ:** идентификатор, источник (пассажирская форма, сотрудник или Android-звонок), имя (обязательно для пассажирской заявки, может быть пустым у операторского заказа), телефон, количество мест, направление, адрес Гори, фиксированная точка, запрошенные дата и время, назначенный слот, статус, отметка удаления, даты создания и изменения.
- **История действий:** заказ, сотрудник, действие, время и необходимые сведения об изменении.
- **Устройство звонков:** идентификатор, название, активность, хеш токена подключения, время последней связи.
- **Телефонное обращение:** идентификатор, устройство и идентификатор события, телефон, время звонка, длительность, отметка удаления, ссылка на созданный заказ. До преобразования не содержит обязательных параметров поездки.
- **Профиль пассажира:** нормализованный телефон, сохранённое имя, последний адрес Гори, отдельный последний адрес посадки в Гори, последняя точка посадки в Тбилиси и время обновления сотрудником. Адрес посадки в Гори восстанавливается только из подтверждённых поездок Гори → Тбилиси. Профиль используется только через защищённые административные запросы.

Статус и отметка удаления хранятся отдельно: это позволяет восстановить прежнее состояние. Лимит вместимости слота в модель не закладывается.

## 8. Сценарии приёмки

1. Пассажир бронирует без регистрации через три шага грузинской формы. Незавершённый шаг не пропускается; возврат сохраняет введённые данные. Счётчик пассажиров ограничен 1–4. Заявка отправляется только с последнего шага и появляется во входящих со статусом ожидания; повтор при сетевой ошибке не создаёт дубликат.
2. Для Гори → Тбилиси форма принимает текстовый адрес посадки в Гори и фиксирует высадку в Дидубе. Для обратного направления обязательны точка посадки в Тбилиси и текстовый адрес высадки в Гори.
3. На обычную будущую дату в обоих направлениях доступны все 18 базовых времён, включая 08:30 и 09:30.
4. Сотрудник назначает входящую заявку в слот. Она исчезает из очереди и появляется в слоте подтверждённой; повторное действие не создаёт дубликат.
5. Ручное создание заказа или преобразование звонка без имени сразу создаёт подтверждённый заказ. Количество мест от 1 до 8 выбирается видимыми кнопками и сохраняется; 0, 9 и дробные значения сервер не принимает. Новый слот доступен только на сегодня или завтра; прошедшие часы сегодня скрыты и не принимаются сервером. Пассажирская форма сохраняет имя, календарь и лимит 1–4.
6. Добавление заказов в слот не блокируется из-за числа заказов или суммы мест.
7. Изменение постоянного расписания и изменение одной даты применяются к соответствующим направлениям и датам; изменение одной даты не меняет остальные даты.
8. Удаление переносит заказ в историю без потери данных. Статус ожидания или подтверждения сохраняется отдельно от отметки удаления. Ожидающая заявка восстанавливается во входящие; подтверждённый заказ — в прежний действующий слот, включая прошлую дату, либо выбранный сотрудником альтернативный слот.
9. Печать всего дня включает заказы со всех страниц и игнорирует поиск таблицы. Печать выбранного времени включает только этот слот. В обоих режимах исключены ожидающие и удалённые заказы; полные адреса, формат телефона и итог мест сохраняются. При ошибке свежей загрузки печать предыдущего списка не начинается.

Дополнительные проверки defaults: отключение слота не удаляет заказы; прошлые времена не принимаются для новой пассажирской заявки; все сотрудники имеют одинаковые права; публичные запросы не возвращают списки заказов или данные пассажиров. Ни один сценарий не требует SMS, уведомлений, оплаты или назначения водителя.

Сценарии повторного пассажира:

1. После сохранения заказа сотрудником повторный номер в другом поддерживаемом формате находит тот же профиль. Последний адрес Гори и действующая точка Тбилиси доступны в ручном заказе и карточке звонка. Изменённые или очищенные вручную адресные поля не перезаписываются автоподстановкой; прежнее имя профиля сохраняется без поля имени в форме.
2. Новые дата, время, направление и количество мест выбираются заново. Отключённая точка не становится доступной для нового заказа из-за сохранённого профиля.
3. Необработанная заявка с публичного сайта не меняет существующий профиль. Без входа поиск профиля по номеру и административные списки недоступны.

Сценарии Android-источника:

1. Синтетическое событие ответа на входящий SIM-звонок от подключённого устройства создаёт одно телефонное обращение. Завершение и повтор обеих фаз возвращают тот же идентификатор; пропущенный звонок не создаёт обращение.
2. Повторная доставка события сохраняет единственное обращение. Оно не назначается в слот и не становится бронью автоматически.
3. Сотрудник оформляет обращение прямо в строке: выбирает один из двух городов, проверяет соответствующий адрес посадки, выбирает 1–8 мест, день и время из карусели. «Сегодня / Завтра» и календарь другой будущей даты работают в обоих направлениях. Подтверждение создаёт ровно один заказ, связывает обращение и убирает его из входящих.
4. Удаление необработанного обращения сохраняет его в истории; восстановление возвращает во входящие. Отключённое устройство не может присылать новые события.
5. На физическом Redmi с Android 15 отдельно проверяются принятый входящий SIM-звонок, исключение пропущенных/исходящих звонков, отсутствие импорта истории и доставка после восстановления связи. Этот сценарий нельзя заменить синтетическим тестом сервера.
6. После поездки Гори → Тбилиси и последующей поездки Тбилиси → Гори в очереди сохраняются разные адреса посадки и высадки в Гори. Переключение города подставляет нужный адрес или остановку. Завершение звонка и обновление очереди не меняют вручную заполненные поля.
7. Большая очередь разбита на страницы; переход между страницами сохраняет черновики. Расписание запрашивается совместно для одинаковых направления и даты, а не отдельно для каждого обращения. Прошедший или отключённый час нельзя подтвердить; повтор подтверждения не дублирует заказ.

## 9. Значения и решения для уточнения

- Реальные названия и адреса 3–4 точек посадки в Тбилиси. До их ручного заполнения используются три демонстрационные точки.
- Точное место высадки в Дидубе: вносится позднее через настройки.
- Defaults раздела 6 реализуются сейчас, но не обозначают отдельного согласования пользователем каждой детали.
- Правила ручного «кастомного» заказа, если подразумевается время вне действующего расписания. Текущий черновик описывает ручной заказ внутри слота.
- Физическая проверка Android-источника на Redmi Android 15 остаётся отдельным этапом при доступе к устройству.

Способ уведомления о подтверждении и SMS-проверка телефона относятся к отложенным решениям и не являются незаполненными требованиями первой реализации формы.

## 10. Порядок сборки

1. Использовать максимум 8 мест в операторских формах и 4 в пассажирской, а также явно обозначенные demo-точки; реальные точки сотрудник внесёт вручную. Defaults раздела 6 применяются к первой реализации.
2. Подготовить структуру приложения, базу данных и вход сотрудников.
3. Реализовать расписание, входящую очередь, подтверждение, ручные заказы и историю.
4. Собрать грузинскую пассажирскую форму и адаптацию для мобильных экранов.
5. Выполнить сценарии приёмки и проверить сохранность данных при работе нескольких сотрудников.

Публичный интерфейс оформляется в стиле GreenTaxi. Внешний вид административной панели опирается на предоставленный макет.

## 11. Техническая основа и запуск

- Node.js 24.x. Клиент: React, TypeScript, Vite. API: Express, TypeScript. Production-база: Neon PostgreSQL через `DATABASE_URL`.
- Локальная разработка без `DATABASE_URL` использует SQLite через встроенный модуль Node.js. По умолчанию данные находятся в `.data/greentaxi.sqlite`, путь задаётся через `DB_PATH`; каталог и файл базы исключены из Git.
- Для Vercel PostgreSQL обязателен: serverless-файловая система не используется для хранения заказов. Сессии и профили также сохраняются в базе, а не в памяти функции.
- `api/index.ts` обслуживает API и переиспользует инициализированное приложение; `vercel.json` задаёт Vite-сборку и маршрутизацию API/SPA. Серверный вход Vercel не запускает Vite dev-сервер.
- Разработка: `npm ci`, затем `npm run dev`; порт по умолчанию — 3000.
- Миграции: `NODE_ENV=production npm run db:migrate` с защищённо заданным `DATABASE_URL`. Схема и начальные настройки создаются идемпотентно под PostgreSQL advisory lock; `npm run build` не запускает миграцию автоматически.
- Production: `npm run build`, миграция базы, затем `npm start` для обычного сервера либо deployment на Vercel. Первичная настройка выполняется с `ADMIN_SETUP_TOKEN`, как описано в разделе 6.3.
- Секреты Neon и первичной настройки задаются в Production Environment Variables и не попадают в клиентские `VITE_*` переменные. PostgreSQL TLS сохраняет проверку сертификата; production не отключает её.
- Preview не использует production-данные. Итоговый production-домен доступен пассажирам и Android без Vercel login; административные API защищены входом приложения.
- Порядок создания проектов и публикации: [Vercel + Neon](deployment-vercel-neon.md). Наличие конфигурации не подтверждает размещение: нужен успешный production-запуск и проверка домена/базы.
- Проверки: `npm test` и `npm run test:e2e`. Команды и условия запуска описаны в README; результаты сообщает фактический запуск проверок.
